# Chapter 8: Gazebo Simulation for Humanoid Robots

You've designed a bipedal walking controller for your humanoid robot. It *should* work—the math checks out, the PID gains are tuned, and the trajectory looks smooth in your visualization. But will the robot actually walk? And more importantly, will it fall over?

Instead of risking expensive hardware on an untested controller, you load your robot model into **Gazebo**—a physics-based simulator built for robotics—and watch as your virtual humanoid takes its first steps. It stumbles. You tweak the controller, reset the simulation, and try again. No hardware damage, no downtime. Just rapid iteration toward a working solution.

In this chapter, we'll explore Gazebo: what it is, how it simulates physics and sensors, and how it integrates with ROS 2 to provide a complete testing environment for humanoid robots.

---

## What is Gazebo?

**Gazebo** (previously "Gazebo Classic", now "Gazebo Sim") is an open-source robot simulator focused on **accurate physics simulation** and **seamless ROS 2 integration**. It's the go-to tool for testing control algorithms, navigation stacks, and sensor configurations before deploying on physical robots.

### Key Design Principles

1. **Physics-First Simulation**: Gazebo uses professional physics engines (ODE, Bullet, DART, Simbody) to accurately model rigid body dynamics, contacts, and joint constraints.
2. **Sensor Simulation**: Supports cameras, LiDAR, IMUs, force/torque sensors, and contact sensors with configurable noise and properties.
3. **ROS 2 Native Integration**: Communicates with ROS 2 nodes via topics, services, and actions—your robot control code doesn't know it's running in simulation.
4. **Plugin Architecture**: Extend functionality with C++ plugins for custom sensors, actuators, and world behaviors.

### When to Use Gazebo

Use Gazebo when you need to:
- Test **control algorithms** (walking, balancing, manipulation).
- Validate **navigation stacks** (path planning, obstacle avoidance).
- Simulate **contact dynamics** (foot-ground interaction, grasping).
- Prototype **sensor configurations** (camera placement, LiDAR range).

**Not ideal for**: Photorealistic rendering, large-scale AI training (Unity or NVIDIA Isaac Sim are better choices).

## Gazebo Architecture

Gazebo separates the simulation engine from visualization and communication layers, allowing flexible deployment.

### Core Components

1. **Gazebo Server (gzserver)**: Runs physics simulation, sensor models, and world updates. Headless (no GUI) for faster execution.
2. **Gazebo Client (gzclient)**: Provides 3D visualization of the simulated world. Optional—you can run simulations without visualization.
3. **SDF (Simulation Description Format)**: XML-based format for describing robots (links, joints, sensors) and worlds (terrain, obstacles, lighting).
4. **Plugins**: C++ libraries that extend Gazebo's capabilities (custom sensors, model behaviors, communication bridges).

### Data Flow in a Typical Simulation

```
ROS 2 Node (Control Code)
   ↓
ROS 2 Topic (e.g., /cmd_vel)
   ↓
Gazebo ROS Bridge (ros_gz_bridge)
   ↓
Gazebo Plugin (processes commands)
   ↓
Gazebo Server (updates physics)
   ↓
Simulated Robot (moves in world)
   ↓
Sensor Plugin (generates sensor data)
   ↓
ROS 2 Topic (e.g., /camera/image, /imu/data)
   ↓
ROS 2 Node (Perception/Control)
```

Your control code publishes velocity commands to `/cmd_vel`. Gazebo receives them, simulates the robot's motion, and publishes sensor data back to ROS 2 topics. Your code doesn't need modifications—it thinks it's talking to a real robot.

## Simulating Humanoid Robots in Gazebo

Humanoid robots present unique simulation challenges due to their complexity. Let's break down how Gazebo handles key aspects.

### 1. Robot Model Definition (URDF/SDF)

Humanoid robots are described using **URDF** (Unified Robot Description Format) or **SDF** (Simulation Description Format). These XML files define:
- **Links**: Rigid body parts (torso, thigh, shin, foot).
- **Joints**: Connections between links (revolute for knee, continuous for hip).
- **Inertial properties**: Mass, center of mass, inertia tensor.
- **Collision geometry**: Simplified shapes for physics calculations.
- **Visual geometry**: Detailed meshes for rendering.

**Example (simplified humanoid leg joint)**:
```xml
<joint name="left_hip_pitch" type="revolute">
  <parent link="torso"/>
  <child link="left_thigh"/>
  <axis xyz="0 1 0"/>  <!-- Pitch axis -->
  <limit lower="-1.57" upper="1.57" effort="100" velocity="5"/>
</joint>
```

Gazebo reads this model and creates a corresponding dynamic simulation with proper mass distribution and joint constraints.

### 2. Physics Simulation

Gazebo steps the physics simulation at a fixed rate (e.g., 1000 Hz) and solves:
- **Rigid body dynamics**: Newton-Euler equations for link motion.
- **Joint constraints**: Enforces joint limits and degrees of freedom.
- **Contact dynamics**: Detects collisions (foot-ground, hand-object) and resolves contact forces.

**Critical for Humanoids**:
- **Contact friction**: Foot-ground friction determines if the robot slips during walking.
- **Joint damping and friction**: Realistic actuator models prevent instantaneous movement.
- **Gravity**: Humanoids must constantly fight gravity to maintain balance.

**Physics Engine Options**:
- **ODE** (Open Dynamics Engine): Fast, stable, good for wheeled robots.
- **Bullet**: Better for complex contact scenarios (grasping).
- **DART**: Best for articulated systems with many joints (humanoids, quadrupeds).

### 3. Sensor Simulation

Gazebo simulates sensors by querying the world state and generating synthetic data.

#### Camera Sensor

```xml
<sensor name="head_camera" type="camera">
  <update_rate>30</update_rate>
  <camera>
    <horizontal_fov>1.047</horizontal_fov>  <!-- 60 degrees -->
    <image>
      <width>640</width>
      <height>480</height>
    </image>
  </camera>
  <plugin name="camera_plugin" filename="libgazebo_ros_camera.so">
    <ros>
      <remapping>image_raw:=/camera/image</remapping>
    </ros>
  </plugin>
</sensor>
```

Gazebo renders the scene from the camera's perspective and publishes RGB images to `/camera/image`. You can add:
- **Noise**: Gaussian noise, motion blur.
- **Lens distortion**: Radial and tangential distortion models.

#### IMU (Inertial Measurement Unit)

IMUs measure linear acceleration and angular velocity. Gazebo simulates:
- **Accelerometer**: Measures acceleration (gravity + robot motion).
- **Gyroscope**: Measures angular velocity.
- **Noise**: White noise, bias drift.

**Critical for Humanoids**: IMUs are essential for balance control. The robot uses IMU data to estimate its orientation and detect falls.

#### Force/Torque Sensors

Attached to feet or hands to measure contact forces. Useful for:
- **Foot contact detection**: Is the foot on the ground?
- **Grasping force**: How tightly is the robot holding an object?

### 4. Joint Control

Gazebo provides multiple control modes:

#### Position Control (Most Common)

You command a target joint position; Gazebo applies torques to reach it.

```cpp
// Pseudo-code: ROS 2 node commands joint position
joint_position_msg.position = 1.57;  // 90 degrees
joint_position_pub.publish(joint_position_msg);
```

Gazebo's plugin receives this command and uses a PID controller to move the joint.

#### Velocity Control

Command target joint velocity; Gazebo applies torques to maintain it.

#### Effort (Torque) Control

Directly command joint torques. Most realistic but requires careful tuning.

## Gazebo + ROS 2: A Complete Example

Let's walk through a typical humanoid simulation workflow.

### Step 1: Create the World

Define a world file (`humanoid_world.sdf`) with ground plane, obstacles, and lighting:

```xml
<world name="humanoid_world">
  <model name="ground_plane">
    <static>true</static>
    <link name="link">
      <collision name="collision">
        <geometry><plane><normal>0 0 1</normal></plane></geometry>
      </collision>
    </link>
  </model>
</world>
```

### Step 2: Load the Humanoid Model

Spawn your humanoid URDF into the world:

```bash
ros2 run gazebo_ros spawn_entity.py -entity my_humanoid -file humanoid.urdf
```

### Step 3: Launch Gazebo with ROS 2 Bridge

```bash
ros2 launch gazebo_ros gazebo.launch.py world:=humanoid_world.sdf
```

Gazebo starts, loads the world, and establishes communication with ROS 2.

### Step 4: Run Control Nodes

Your ROS 2 control nodes (from Chapter 6) subscribe to `/imu/data` and `/joint_states`, compute control commands, and publish to `/joint_commands`. Gazebo executes these commands and updates the simulation.

### Step 5: Monitor with RViz

Visualize sensor data, joint states, and TF transforms in RViz (ROS visualization tool) while Gazebo runs the physics simulation.

## Gazebo for Humanoid Development: Use Cases

### 1. Bipedal Walking Controller Testing

**Scenario**: You've implemented a Zero Moment Point (ZMP) walking controller.

**Gazebo Test**:
- Load humanoid in flat ground world.
- Command robot to walk forward 5 meters.
- Monitor foot contact forces, CoM (center of mass) trajectory, and joint torques.
- **Success criteria**: Robot walks without falling, maintains balance.

**Advantages**:
- Test on slopes, uneven terrain, stairs (change world geometry).
- Simulate sensor failures (e.g., IMU dropout) to test robustness.
- Run 100 trials in parallel (headless mode) to collect statistics.

### 2. Manipulation and Grasping

**Scenario**: Test arm control for picking up objects.

**Gazebo Test**:
- Place objects (cubes, cylinders) on table.
- Command arm to reach, grasp, and lift.
- Monitor grasp forces, object slip detection.

**Advantages**:
- Test different object shapes, weights, and materials (friction coefficients).
- Debug inverse kinematics without risk of collisions.
- Validate MoveIt 2 motion planning in simulation before deployment.

### 3. Navigation in Cluttered Environments

**Scenario**: Test Nav2 (ROS 2 navigation stack) for humanoid navigation.

**Gazebo Test**:
- Create world with narrow corridors, doorways, furniture.
- Command humanoid to navigate from point A to point B.
- Monitor obstacle avoidance, path planning, goal reaching.

**Advantages**:
- Test edge cases (moving obstacles, sensor occlusion) safely.
- Validate costmap configuration (inflation radius, obstacle layers).

## Limitations of Gazebo

Despite its strengths, Gazebo has limitations:

1. **Computational Cost**: Accurate contact dynamics are expensive; complex scenes slow down simulation.
2. **Visual Realism**: Not photorealistic; unsuitable for training vision models on real-world appearance.
3. **Sim-to-Real Gap**: Contact parameters (friction, damping) are hard to calibrate perfectly; simulated behavior may differ from reality.

**Solutions**:
- **Parallel with Unity**: Use Gazebo for dynamics, Unity for perception training.
- **Domain randomization** (Chapter 10): Vary simulation parameters to improve real-world generalization.
- **Hardware-in-the-loop testing**: Run controllers in Gazebo, but feed in real sensor data.

## Summary

Gazebo is the gold standard for **physics-based simulation** in robotics. It provides:
- Accurate rigid body dynamics and contact simulation.
- Comprehensive sensor models (cameras, LiDAR, IMU, force sensors).
- Seamless ROS 2 integration via topics, services, and actions.
- Flexible plugin architecture for custom extensions.

For humanoid robotics, Gazebo is indispensable for testing **bipedal locomotion**, **whole-body control**, and **manipulation** before deploying on physical hardware. While it's not perfect (visual realism and sim-to-real gap remain challenges), it dramatically accelerates development by enabling safe, fast, and repeatable testing.

In Chapter 9, we'll explore **Unity**—a complementary tool that excels at **photorealistic rendering** and **perception training**. Together, Gazebo and Unity cover the full spectrum of humanoid development needs.
