Chapter 4: ROS 2 Core Concepts - Nodes, Topics, and Messages

Learning Objectives​

By the end of this chapter, you will be able to:

  • Define nodes, topics, and messages in ROS 2
  • Understand the publish-subscribe communication pattern
  • Map ROS 2 concepts to humanoid robot subsystems
  • Diagram a simple multi-node ROS 2 system

Introduction​

In Chapter 3, we learned that ROS 2 is middleware that connects robot components. But how does this connection work? What are the actual building blocks of a ROS 2 system?

Every ROS 2 application is built from three fundamental primitives:

  1. Nodes: Independent programs that perform specific tasks (e.g., reading sensor data, computing navigation paths)
  2. Topics: Named channels through which nodes exchange data (e.g., /camera/image, /joint_states)
  3. Messages: Data structures sent over topics (e.g., an image, a list of joint angles)

Think of nodes as workers in a factory, topics as conveyor belts connecting workstations, and messages as the parts moving along those belts. Each worker (node) does one job well, and they communicate by passing parts (messages) along designated conveyor belts (topics).

In this chapter, we'll explore each of these concepts in detail and see how they combine to create a complete robotic system.

Nodes: The Building Blocks​

A node is an independent executable process that performs a specific function within a ROS 2 system. Each node is responsible for one task—and one task only. This principle, called single responsibility, makes systems modular and easier to debug.

What is a Node?​

Examples of nodes in a humanoid robot:

  • Camera driver node: Reads images from a camera and publishes them to a topic
  • Object detector node: Subscribes to camera images, detects objects, publishes object locations
  • Navigation planner node: Computes collision-free paths and publishes velocity commands
  • Joint controller node: Subscribes to velocity commands, sends motor signals to actuators
  • Balance controller node: Reads IMU data, adjusts joint torques to maintain stability

Each node runs as a separate process (or thread), which means:

  • Nodes can run on different computers (distributed computing)
  • If one node crashes, others continue running
  • You can start, stop, or restart individual nodes without affecting the rest of the system

Node Lifecycle​

ROS 2 nodes have a lifecycle with well-defined states:

  1. Unconfigured: Node exists but hasn't loaded resources (e.g., hasn't opened camera)
  2. Inactive: Resources loaded but node isn't processing data
  3. Active: Node is running and processing data
  4. Finalized: Node is shutting down, releasing resources

This lifecycle enables graceful startup and shutdown. For example, a camera node can:

  • Load camera drivers in the "Inactive" state
  • Verify the camera is connected
  • Only transition to "Active" once ready to publish images

Creating Nodes: Conceptual Example​

Here's a simplified pseudo-code example of a ROS 2 node:

class CameraNode:
    def __init__(self):
        # Initialize ROS 2 node with name "camera_driver"
        self.node = rclpy.create_node('camera_driver')

        # Create a publisher for camera images
        self.image_publisher = self.node.create_publisher(
            topic='/camera/image',
            message_type=Image
        )

        # Open camera hardware
        self.camera = Camera(device_id=0)

    def run(self):
        while rclpy.ok():
            # Capture image from camera
            image = self.camera.capture()

            # Publish image to the topic
            self.image_publisher.publish(image)

            # Wait for next frame
            sleep(0.033)  # ~30 FPS

Key takeaway: Each node does one thing (e.g., "publish camera images") and does it well. Complex robot behaviors emerge from many simple nodes working together.

Topics: Communication Channels​

A topic is a named channel through which nodes exchange messages. Topics implement the publish-subscribe pattern: one or more nodes publish data to a topic, and one or more nodes subscribe to receive that data.

How Topics Work​

Publishers and Subscribers:

  • A publisher sends messages to a topic (e.g., camera node publishes images to /camera/image)
  • A subscriber receives messages from a topic (e.g., object detector subscribes to /camera/image)

Key Properties:

  1. Asynchronous: Publishers don't wait for subscribers. If no one is listening, messages are sent anyway (and ignored)
  2. Many-to-many: Multiple publishers can send to the same topic, and multiple subscribers can listen
  3. Typed: Each topic has a message type (e.g., sensor_msgs/Image). Publishers and subscribers must use the same type

Example: Camera Topic

┌─────────────────┐        /camera/image       ┌───────────────────┐
│  Camera Node    │ ──────────────────────────>│ Object Detector   │
│  (Publisher)    │  (sensor_msgs/Image)       │  (Subscriber)     │
└─────────────────┘                            └───────────────────┘
  • The camera node publishes images to /camera/image at 30 Hz
  • The object detector subscribes to /camera/image and processes each frame
  • If you add a second subscriber (e.g., a recording node), it also receives images—without any changes to the camera node

Topic Naming Conventions​

ROS 2 uses hierarchical topic names with forward slashes:

  • /camera/image: Image from the main camera
  • /camera/depth: Depth data from the same camera
  • /left_arm/joint_states: Joint angles for the left arm
  • /right_arm/joint_states: Joint angles for the right arm

This hierarchy makes large systems organized and prevents naming conflicts.

Quality of Service (QoS)​

Not all data is equally important. Some data (like control commands) must arrive reliably, while other data (like camera images) can tolerate occasional drops if it reduces latency.

ROS 2 supports QoS policies that control how messages are delivered:

  • Reliability: "Reliable" (guaranteed delivery, resend if lost) vs. "Best Effort" (send once, don't retry)
  • Durability: "Transient Local" (cache last N messages for late joiners) vs. "Volatile" (only new messages)
  • History: Keep last 10 messages vs. keep all messages
  • Deadline: Maximum time between messages (e.g., IMU data must arrive every 10ms)

Example:

  • Camera images: Best Effort (latest frame matters more than old frames)
  • Control commands: Reliable (missing a command could cause unsafe behavior)
  • IMU data: Deadline 10ms (balance controller needs timely data)

Messages: Data Structures​

A message is a data structure sent over topics. Messages define what information is exchanged between nodes.

Standard Message Types​

ROS 2 provides standard message packages:

  • sensor_msgs: Sensor data (Image, PointCloud2, Imu, JointState)
  • geometry_msgs: Geometric primitives (Point, Pose, Twist, Transform)
  • std_msgs: Basic types (String, Int32, Float64, Bool)
  • nav_msgs: Navigation data (Odometry, Path, OccupancyGrid)

Example: sensor_msgs/Image

Header header          # Timestamp and frame ID
uint32 height          # Image height in pixels
uint32 width           # Image width in pixels
string encoding        # Pixel format (e.g., "rgb8", "bgr8")
uint8[] data           # Raw image data

This message describes an image. A camera driver fills in the fields (width, height, pixel data) and publishes it to a topic. Subscribers receive this structured data and can access fields by name.

Custom Messages​

If standard messages don't fit your needs, you can define custom messages. For example, a humanoid robot might define:

# HumanoidState.msg
Header header
float64[] joint_positions      # Current joint angles (radians)
float64[] joint_velocities     # Current joint speeds (rad/s)
geometry_msgs/Pose base_pose   # Base position and orientation
bool is_balanced               # Balance status

Custom messages are defined in .msg files and compiled into code (Python, C++) that nodes can use.

Message Design Best Practices​

  • Include timestamps: Add a Header with timestamp so subscribers know when data was captured
  • Use SI units: Meters (not feet), radians (not degrees), seconds (not milliseconds)
  • Keep messages focused: One message type per logical data unit (don't mix unrelated data)

Putting It Together: Humanoid Robot Example​

Let's see how nodes, topics, and messages combine in a real humanoid robot system. We'll build a simplified perception-to-action pipeline.

Scenario: Humanoid Navigating a Room​

Goal: The humanoid needs to navigate to a target location while avoiding obstacles detected by its camera.

System Components (nodes):

  1. Camera Driver Node: Publishes camera images
  2. Obstacle Detector Node: Detects obstacles from images, publishes obstacle locations
  3. Navigation Planner Node: Computes collision-free paths, publishes velocity commands
  4. Motor Controller Node: Executes velocity commands by sending signals to motors

Data Flow (topics and messages):

┌────────────────┐      /camera/image      ┌────────────────┐
│ Camera Driver  │────────────────────────>│ Obstacle       │
│ Node           │  (sensor_msgs/Image)    │ Detector Node  │
└────────────────┘                         └────────────────┘
                                                   │
                                                   │ /obstacles
                                                   │ (geometry_msgs/PoseArray)
                                                   v
                                           ┌────────────────┐
                                           │ Navigation     │
                                           │ Planner Node   │
                                           └────────────────┘
                                                   │
                                                   │ /cmd_vel
                                                   │ (geometry_msgs/Twist)
                                                   v
                                           ┌────────────────┐
                                           │ Motor          │
                                           │ Controller Node│
                                           └────────────────┘

Step-by-Step:

  1. Camera Driver captures frames and publishes sensor_msgs/Image messages to /camera/image at 30 Hz
  2. Obstacle Detector subscribes to /camera/image, runs object detection (e.g., using a neural network), and publishes detected obstacle positions to /obstacles as geometry_msgs/PoseArray
  3. Navigation Planner subscribes to /obstacles, computes a safe path to the goal, and publishes velocity commands (linear_x, angular_z) to /cmd_vel as geometry_msgs/Twist
  4. Motor Controller subscribes to /cmd_vel and translates velocity commands into motor signals (joint torques) for the legs

Key Insights:

  • Each node is independent: The camera driver doesn't know about the navigation planner, and the motor controller doesn't know about the obstacle detector
  • Nodes are reusable: If you want to record camera images for later analysis, add a new subscriber to /camera/image without modifying existing nodes
  • The system is modular: You can swap the obstacle detector (e.g., upgrade from a simple algorithm to a deep learning model) by replacing that single node

###Adding More Nodes

Want to add balance control? Add a Balance Controller Node:

  • Subscribes to /imu/data (accelerometer/gyroscope readings)
  • Publishes /joint_corrections (torque adjustments to maintain balance)
  • The Motor Controller subscribes to both /cmd_vel and /joint_corrections and combines them

The existing nodes (camera, obstacle detector, navigation planner) don't change at all—you've extended the system by adding a new node and topic.

Visualizing the System​

ROS 2 provides tools to visualize node-topic connections:

rqt_graph: Graphical tool that shows nodes (circles) and topics (arrows). Running rqt_graph on the humanoid example above displays the data flow visually.

ros2 topic list: Lists all active topics:

/camera/image
/obstacles
/cmd_vel
/imu/data
/joint_corrections

ros2 node list: Lists all running nodes:

/camera_driver
/obstacle_detector
/navigation_planner
/motor_controller
/balance_controller

These tools are invaluable for debugging: if data isn't flowing as expected, you can quickly see if a topic is missing or a node isn't running.

Summary​

In this chapter, we explored the core building blocks of ROS 2:

Nodes: Independent processes that perform specific tasks (e.g., read sensor, compute plan, control motor). Each node follows the single-responsibility principle, making systems modular and maintainable.

Topics: Named channels that connect nodes using the publish-subscribe pattern. Topics enable asynchronous, many-to-many communication. Publishers send data without waiting for subscribers, and subscribers receive data without knowing who sent it.

Messages: Typed data structures sent over topics (e.g., sensor_msgs/Image, geometry_msgs/Twist). ROS 2 provides standard message types for common data (sensors, geometry, navigation), and you can define custom messages for specialized needs.

System Integration: In a humanoid robot, these primitives combine to create complex behaviors. A camera node publishes images, an obstacle detector processes them and publishes obstacle locations, a navigation planner computes safe paths and publishes velocity commands, and a motor controller executes those commands. Each node is independent, reusable, and replaceable.

Key takeaways:

  • Modularity: Each node does one thing well
  • Decoupling: Nodes don't know about each other, only topics
  • Scalability: Add new functionality by adding nodes
  • Debuggability: Tools like rqt_graph visualize system structure

With nodes, topics, and messages, you can build sophisticated robotic systems from simple, composable components. But what if you need synchronous request-response communication instead of asynchronous publish-subscribe? Or what if you need to track progress of a long-running task? In Chapter 5, we'll explore ROS 2 services and actions, which complement topics for different communication patterns.
